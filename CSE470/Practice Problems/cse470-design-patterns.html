Design Patterns — practice problems & solutions

Fifteen problems on Observer, Singleton, Adapter and Factory Method — eight that drill one pattern each, seven that make two patterns work together. Every solution comes with a UML class diagram, a reference implementation in both Python and Java, the real program output, the participant table, and the marking points.

The four patterns

Observer

Define a one-to-many dependency so that when one object changes state, all its dependents are notified automatically.

Removes the coupling fault: the subject stops knowing who is listening.

Drilled in: The Section Notice Board, The Online Auction Room, Campus Alert Hub, Flood Warning Station

Singleton

Ensure a class has only one instance, and provide a global point of access to it.

Removes the scarcity / shared-state fault: one sequence, one connection, one cache.

Drilled in: One Grade Database, One Print Spooler for the Lab, Campus Alert Hub, The Card Reader, The Campus SMS Gateway, The Currency Desk, IT Helpdesk Tickets

Adapter

Convert the interface of a class into another interface clients expect.

Removes the vocabulary fault: the client stops speaking the vendor's language.

Drilled in: Checkout with Two Payment Vendors, Two Book Search Back-ends, Flood Warning Station, The Upload Service, The Card Reader, The Campus SMS Gateway, The Currency Desk

Factory Method

Define an interface for creating an object, but let subclasses decide which class to instantiate.

Removes the selection fault: the shared routine stops deciding what to build.

Drilled in: The Courier Branch, The Result Export Portals, The Upload Service, IT Helpdesk Tickets

Observer

Intent

Define a one-to-many dependency so that when one object changes state, all its dependents are notified automatically.

Four classes, always in this order. Observer is the interface the subject calls back through. Subject is a concrete base class that owns the list and the three list operations — you write it once and never change it. ConcreteSubject extends it, holds the real state, and calls notify() at the end of every state-changing operation. The concrete observers implement update and read the state back out through the subject's getters.

RoleWhat it doesNotes
ObserverThe callback interface. One abstract method, update(subject).Nothing else ever goes here.
SubjectOwns _observers, attach, detach, notify. Identical in every problem.Note __init__ lives here, not in the child.
ConcreteSubjectExtends Subject. Holds the state, and calls self.notify() at the end of each state change.Must call super().__init__().
Concrete ObserversImplement update(subject) and read state through the subject's getters.They never read each other.

from abc import ABC, abstractmethod


# ---------- Observer interface ----------
class Observer(ABC):
    @abstractmethod
    def update(self, subject):
        pass


# ---------- Subject ----------
class Subject:
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        if observer in self._observers:
            self._observers.remove(observer)

    def notify(self):
        for observer in self._observers:
            observer.update(self)


# ---------- Concrete Subject ----------
class ConcreteSubject(Subject):
    def __init__(self):
        super().__init__()          # never forget this line
        self._state = None

    def change(self, value):        # the state-changing operation ...
        self._state = value
        self.notify()               # ... always ends with notify()

    def get_state(self):            # one reader per piece of state
        return self._state


# ---------- Concrete Observers ----------
class ConcreteObserverA(Observer):
    def update(self, subject):
        state = subject.get_state()          # pull, then print
        print(f"A saw {state}")


class ConcreteObserverB(Observer):
    def update(self, subject):
        state = subject.get_state()
        print(f"B saw {state}")


if __name__ == "__main__":
    subject = ConcreteSubject()
    a = ConcreteObserverA()
    b = ConcreteObserverB()

    subject.attach(a)
    subject.attach(b)
    subject.change("first")

    subject.detach(b)
    subject.change("second")

import java.util.ArrayList;
import java.util.List;

// ---------- Observer interface ----------
interface Observer {
    void update(Subject subject);
}

// ---------- Subject ----------
class Subject {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    // NOT called notify() -- Object.notify() is final in Java
    public void notifyObservers() {
        for (Observer observer : new ArrayList<>(observers)) {
            observer.update(this);
        }
    }
}

// ---------- Concrete Subject ----------
class ConcreteSubject extends Subject {
    private String state;

    public void change(String value) {   // the state-changing operation ...
        this.state = value;
        notifyObservers();               // ... always ends with notifyObservers()
    }

    public String getState() {           // one reader per piece of state
        return state;
    }
}

// ---------- Concrete Observers ----------
class ConcreteObserverA implements Observer {
    @Override
    public void update(Subject subject) {
        String state = ((ConcreteSubject) subject).getState();   // pull, then print
        System.out.println("A saw " + state);
    }
}

class ConcreteObserverB implements Observer {
    @Override
    public void update(Subject subject) {
        String state = ((ConcreteSubject) subject).getState();
        System.out.println("B saw " + state);
    }
}

public class ObserverSkeleton {
    public static void main(String[] args) {
        ConcreteSubject subject = new ConcreteSubject();
        ConcreteObserverA a = new ConcreteObserverA();
        ConcreteObserverB b = new ConcreteObserverB();

        subject.attach(a);
        subject.attach(b);
        subject.change("first");

        subject.detach(b);
        subject.change("second");
    }
}
Output
A saw first
B saw first
A saw second

Rules that hold in every Observer solution

  • Subject.__init__ creates the list. The concrete subject calls super().__init__() — forgetting that line is the single most common bug in this pattern.
  • The state-changing method ends with self.notify(). Nothing else calls notify().
  • update takes the subject, not the data. The observer pulls what it needs through the getters, so adding a new field does not change the Observer interface.
  • One getter per piece of state, named the same in Python and Java.
  • The subject never knows a concrete observer type, and never imports one.

Singleton

Intent

Ensure a class has only one instance, and provide a global point of access to it.

One class plus its clients. The instance lives on the class, creation is guarded, and the clients never build one — they ask for it. The printed line inside the creation guard is there so you can see that it happens once; in a real singleton it would be the expensive thing you are trying not to repeat.

Python and Java disagree here more than anywhere else. Python overrides __new__; Java makes the constructor private and offers getInstance(). Same design, different mechanism.

RoleWhat it doesNotes
SingletonHolds _instance, guards creation, and does the real work.Everything one-per-program lives here.
ClientsAsk for the instance every time they need it. They never store it in a field, and never construct one.Any number of them.

# ---------- Singleton ----------
class Singleton:
    _instance = None                       # the one instance lives on the class

    def __new__(cls):
        if cls._instance is None:          # lazy creation
            print("Creating the one instance...")
            cls._instance = super(Singleton, cls).__new__(cls)
            cls._instance.items = []       # initialise ONCE, here
        return cls._instance

    def record(self, item):
        self.items.append(item)
        total = len(self.items)
        print(f"recorded {item} (total {total})")

    def count(self):
        return len(self.items)


# ---------- Clients: each one asks for the instance independently ----------
class ClientA:
    def use(self, item):
        Singleton().record(item)


class ClientB:
    def report(self):
        count = Singleton().count()
        print(f"total so far: {count}")


if __name__ == "__main__":
    print("--- nothing created yet ---")

    ClientA().use("first")
    ClientA().use("second")
    ClientB().report()

    same = Singleton() is Singleton()
    print("same object?", same)

import java.util.ArrayList;
import java.util.List;

// ---------- Singleton ----------
class Singleton {
    private static Singleton instance;                  // the one instance
    private final List<String> items = new ArrayList<>();

    private Singleton() {                               // nobody else can build one
        System.out.println("Creating the one instance...");
    }

    public static Singleton getInstance() {             // lazy creation
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }

    public void record(String item) {
        items.add(item);
        int total = items.size();
        System.out.println("recorded " + item + " (total " + total + ")");
    }

    public int count() {
        return items.size();
    }
}

// ---------- Clients: each one asks for the instance independently ----------
class ClientA {
    public void use(String item) {
        Singleton.getInstance().record(item);
    }
}

class ClientB {
    public void report() {
        int count = Singleton.getInstance().count();
        System.out.println("total so far: " + count);
    }
}

public class SingletonSkeleton {
    public static void main(String[] args) {
        System.out.println("--- nothing created yet ---");

        new ClientA().use("first");
        new ClientA().use("second");
        new ClientB().report();

        boolean same = Singleton.getInstance() == Singleton.getInstance();
        System.out.println("same object? " + same);
    }
}

Rules that hold in every Singleton solution

  • _instance is a class attribute, not an instance attribute.
  • The state is initialised inside the creation guard, so it happens once. Anything you initialise outside the guard is reset on every call.
  • In Python, __init__ still runs on every Singleton() call. If the class needs one, it must start with a guard — see Campus Alert Hub, where forgetting it silently empties the observer list.
  • Clients call Singleton() / Singleton.getInstance() at the point of use. A client that takes the instance as a constructor argument has removed the problem, not solved it.
  • The identity check a is b / a == b is the test that the pattern actually works.

Adapter

Intent

Convert the interface of a class into another interface clients expect.

Four roles. The adaptee is vendor code you are not allowed to touch — that constraint is the whole reason the pattern exists. The target is the interface your client wants to speak. The adapter implements the target and translates each call into whatever the adaptee actually offers. The client is written against the target and never learns a vendor name.

There are two ways to build the adapter. An object adapter holds the adaptee in a field; a class adapter inherits from it. Both appear below, and Checkout with Two Payment Vendors and Two Book Search Back-ends put them side by side. Everywhere else in this pack the object adapter is used, because it keeps the vendor methods off the adapter's public surface.

RoleWhat it doesNotes
AdapteeVendor code. Frozen — you may not edit it, and its method names are wrong for you.One or several.
TargetThe interface the client speaks. You design this one.An ABC in Python, an interface in Java.
AdapterImplements Target, translates each call into adaptee calls. One adapter per adaptee.Named <Vendor>Adapter.
ClientWritten against Target only.Never names a vendor class.

from abc import ABC, abstractmethod


# ---------- Adaptee: vendor code, NOT modified ----------
class Vendor:
    def open_session(self):
        print("  Vendor: session opened")

    def vendor_call(self, a, b):
        print(f"  Vendor: working with {a} and {b}")
        return "vendor-result"


# ---------- Target ----------
class Target(ABC):
    @abstractmethod
    def request(self, value):
        pass


# ---------- Object Adapter (composition) ----------
class VendorObjectAdapter(Target):
    def __init__(self, adaptee):
        self.adaptee = adaptee                      # holds the adaptee

    def request(self, value):
        self.adaptee.open_session()                 # one target call ->
        return self.adaptee.vendor_call(value, 1)   # two adaptee calls


# ---------- Class Adapter (inheritance) ----------
class VendorClassAdapter(Target, Vendor):
    def request(self, value):
        self.open_session()                         # inherited, not held
        return self.vendor_call(value, 1)


# ---------- Client: speaks Target and nothing else ----------
class Client:
    def run(self, target):
        result = target.request("x")
        print("Client got:", result)


if __name__ == "__main__":
    client = Client()

    client.run(VendorObjectAdapter(Vendor()))
    client.run(VendorClassAdapter())

    String request(String value);

Rules that hold in every Adapter solution

  • The adaptee is never modified. If you edited it, you did not need the pattern.
  • One adapter per adaptee, named after the vendor it wraps and ending in Adapter.
  • The object adapter holds the vendor object in a field called adaptee and calls it. The class adapter inherits and calls the inherited method directly — that is the only difference.
  • Translation is the adapter's whole job: renaming, reordering, folding several vendor calls into one target call, converting units.
  • No vendor method name appears anywhere in the client. That is how you know the adapter is complete.

Factory Method

Intent

Define an interface for creating an object, but let subclasses decide which class to instantiate.

Two parallel hierarchies. On the product side, an abstract Product holds whatever data every product needs and declares the abstract behaviour; each concrete product implements it. On the creator side, an abstract Creator declares the factory method — abstract, the one thing subclasses override — and a concrete template method that does the shared work using whatever the factory method returned.

The template method is the payoff. It is written once, names no concrete product, and contains no if on a type. Adding a fifth product means adding two classes and editing nothing.

RoleWhat it doesNotes
ProductAbstract. Constructor takes the data every product needs; declares the abstract behaviour.ABC in Python, abstract class in Java.
Concrete ProductsOne per variant. Implement the behaviour; add no new public methods.Usually three in these problems.
CreatorAbstract. Declares the abstract factory method and implements the concrete template method.The template method is the point.
Concrete CreatorsOverride the factory method, return one concrete product, and nothing else.One or two lines each.

from abc import ABC, abstractmethod


# ---------- Product ----------
class Product(ABC):
    def __init__(self, data):           # every product is built with its data
        self.data = data

    @abstractmethod
    def describe(self):
        pass


# ---------- Concrete Products ----------
class ProductA(Product):
    def describe(self):
        return f"A({self.data})"


class ProductB(Product):
    def describe(self):
        return f"B({self.data})"


# ---------- Creator ----------
class Creator(ABC):
    @abstractmethod
    def create_product(self, data):     # the factory method
        pass

    def handle(self, data):             # the template method
        product = self.create_product(data)
        description = product.describe()
        print(f"handled {description}")


# ---------- Concrete Creators ----------
class CreatorA(Creator):
    def create_product(self, data):
        return ProductA(data)


class CreatorB(Creator):
    def create_product(self, data):
        return ProductB(data)


if __name__ == "__main__":
    creators = [CreatorA(), CreatorB()]

    for creator in creators:
        creator.handle("input")

  • The template method is concrete on the creator and is never overridden.

class Subject:
    def __init__(self):

        self._observers.append(observer)

Java notes — where the translation is not one-to-one

1.Which of the two adapters could also have wrapped an object you receive at runtime, and why can the other one not?

The object adapter can wrap an instance handed to it at runtime (composition — you can even swap the adaptee later, or wrap a subclass). The class adapter fixes its adaptee at class-definition time through inheritance, so it can only ever adapt that one class.

from abc import ABC, abstractmethod


# ---------- Observer interface ----------
class Observer(ABC):
    @abstractmethod
    def update(self, subject):
        pass


# ---------- Subject ----------
class Subject:
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        if observer in self._observers:
            self._observers.remove(observer)

    def notify(self):
        for observer in self._observers:
            observer.update(self)


# ---------- Concrete Subject ----------
class Auction(Subject):
    def __init__(self, item):
        super().__init__()
        self._item = item
        self._highest_bid = 0
        self._highest_bidder = "nobody"

    def place_bid(self, name, amount):
        if amount > self._highest_bid:
            self._highest_bid = amount
            self._highest_bidder = name
            self.notify()

    def get_item(self):
        return self._item

    def get_highest_bid(self):
        return self._highest_bid

    def get_highest_bidder(self):
        return self._highest_bidder


# ---------- Concrete Observers ----------
class Bidder(Observer):
    def __init__(self, name):
        self.name = name

    def update(self, subject):
        item = subject.get_item()
        amount = subject.get_highest_bid()
        leader = subject.get_highest_bidder()
        tag = "you lead" if leader == self.name else f"{leader} leads"
        print(f"[{self.name}] {item} now BDT {amount} - {tag}")

    def join(self, auction):
        auction.attach(self)
        print(f"{self.name} joined the auction")

    def leave(self, auction):
        auction.detach(self)
        print(f"{self.name} left the auction")


class BidLogger(Observer):
    def __init__(self):
        self.entries = []

    def update(self, subject):
        amount = subject.get_highest_bid()
        leader = subject.get_highest_bidder()
        self.entries.append((amount, leader))
        count = len(self.entries)
        print(f"[Logger] bid #{count} recorded")

    sadia = Bidder("Sadia")

    sadia.join(auction)
    auction.attach(logger)

import java.util.ArrayList;
import java.util.List;

// ---------- Observer interface ----------
interface Observer {
    void update(Subject subject);
}

// ---------- Subject ----------
class Subject {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    public void notifyObservers() {                 // notify() is final on Object
        for (Observer observer : new ArrayList<>(observers)) {
            observer.update(this);
        }
    }
}

// ---------- Concrete Subject ----------
class Auction extends Subject {
    private final String item;
    private int highestBid = 0;
    private String highestBidder = "nobody";

    public Auction(String item) {
        this.item = item;
    }

    public void placeBid(String name, int amount) {
        if (amount > highestBid) {
            highestBid = amount;
            highestBidder = name;
            notifyObservers();
        }
    }

    public String getItem() {
        return item;
    }

    public int getHighestBid() {
        return highestBid;
    }

    public String getHighestBidder() {
        return highestBidder;
    }
}

// ---------- Concrete Observers ----------
class Bidder implements Observer {
    private final String name;

    public Bidder(String name) {
        this.name = name;
    }

    @Override
    public void update(Subject subject) {
        Auction auction = (Auction) subject;
        String item = auction.getItem();
        int amount = auction.getHighestBid();
        String leader = auction.getHighestBidder();
        String tag = leader.equals(name) ? "you lead" : leader + " leads";
        System.out.println("[" + name + "] " + item
                + " now BDT " + amount + " - " + tag);
    }

    public void join(Auction auction) {
        auction.attach(this);
        System.out.println(name + " joined the auction");
    }

    public void leave(Auction auction) {
        auction.detach(this);
        System.out.println(name + " left the auction");
    }
}

class BidLogger implements Observer {
    private final List<String> entries = new ArrayList<>();

    @Override
    public void update(Subject subject) {
        Auction auction = (Auction) subject;
        int amount = auction.getHighestBid();
        String leader = auction.getHighestBidder();
        entries.add(amount + " by " + leader);
        int count = entries.size();
        System.out.println("[Logger] bid #" + count + " recorded");
    }
}

public class AuctionDemo {
    public static void main(String[] args) {
        Auction auction = new Auction("Antique Clock");

        Bidder nabil = new Bidder("Nabil");
        Bidder sadia = new Bidder("Sadia");
        BidLogger logger = new BidLogger();

        nabil.join(auction);
        sadia.join(auction);
        auction.attach(logger);

        auction.placeBid("Nabil", 5000);
        sadia.leave(auction);
        auction.placeBid("Sadia", 7500);
    }
}

Marking points

  • notify() is called from inside place_bid, not from the driver, and only when the bid actually beats the current price.
  • Auction never names Bidder anywhere. If it does, the one-to-many decoupling is not there.
  • The observer reads state back through the subject it was handed (subject.get_highest_bid()) rather than having the price pushed in as an argument — either is defensible, but ask them which one keeps the update signature stable when the subject grows more state.

Java notes — where the translation is not one-to-one

  • Both languages expose one getter per piece of state — getHighestBid() and getHighestBidder() — so the two listings line up method for method. Python could have returned a single tuple and Java a small Price record; pushing the values in as update arguments is the third option. Comparing the three is the pull-vs-push decision the marking notes mention.
  • leader.equals(name), never leader == name. == on strings compares references, and it would appear to work here because of the string pool, then fail the moment a name is read from input. This is the single most common Java bug in first-year code.

Marking points

  • __new__ is overridden, _instance is a class attribute, and the guard is if cls._instance is None — this is what makes it lazy.
  • The start-up message prints once and only after the first client prints. Creating the instance at import time is not lazy.
  • queue is initialised inside the __new__ guard (or with an _initialised flag in __init__). A plain __init__ that assigns self.queue = [] empties the queue on every later call, so the admin console reports 0 jobs. This is the trap in this problem.
  • LabComputer and AdminConsole are untouched.
  • Common alternatives worth accepting: a get_instance() classmethod, a decorator, or a module-level instance — but the clients here call PrintSpooler() directly, so a get_instance() solution has to edit them, which the brief forbids. Worth making them notice that.

Java notes — where the translation is not one-to-one

  • The brief's “do not touch the clients” rule cannot be honoured in Java: with a private constructor, new PrintSpooler() stops compiling, so both clients must move to PrintSpooler.getInstance(). Compare with a2 — the same limitation, and it is the reason getInstance() is the textbook Java form while Python textbooks show __new__.
  • pending() returns the live internal list, so any caller can mutate the queue. Collections.unmodifiableList(queue) (or List.copyOf) is the honest signature — a good one-line follow-up exercise.
  • Python's tuple (pc, filename) becomes a small Job class; from Java 16 on, record Job(String pc, String filename) {} says the same thing in one line.

from abc import ABC, abstractmethod


# ---------- Observer interface ----------
class Observer(ABC):
    @abstractmethod
    def update(self, subject):
        pass


# ---------- Subject ----------
class Subject:
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        if observer in self._observers:
            self._observers.remove(observer)

    def notify(self):
        for observer in self._observers:
            observer.update(self)


# ---------- Singleton + Concrete Subject ----------
class AlertHub(Subject):
    _instance = None

    def __new__(cls):
        if cls._instance is None:                      # lazy creation
            print("Booting campus alert hub...")
            cls._instance = super(AlertHub, cls).__new__(cls)
        return cls._instance

    def __init__(self):
        if hasattr(self, "_level"):                    # already set up: do it once
            return
        super().__init__()                             # Subject: self._observers = []
        self._level = None
        self._latest = None

    def raise_alert(self, level, text):
        self._level = level
        self._latest = text
        self.notify()

    def get_level(self):
        return self._level

    def get_latest(self):
        return self._latest

import java.util.ArrayList;
import java.util.List;

// ---------- Observer interface ----------
interface Observer {
    void update(Subject subject);
}

// ---------- Subject ----------
class Subject {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    public void notifyObservers() {                 // notify() is final on Object
        for (Observer observer : new ArrayList<>(observers)) {
            observer.update(this);
        }
    }
}

// ---------- Singleton + Concrete Subject ----------
class AlertHub extends Subject {
    private static AlertHub instance;
    private String level;
    private String latest;

    private AlertHub() {                            // runs exactly once, ever
        System.out.println("Booting campus alert hub...");
    }

    public static AlertHub getInstance() {          // lazy creation
        if (instance == null) {
            instance = new AlertHub();
        }
        return instance;
    }

    public void raiseAlert(String level, String text) {
        this.level = level;
        this.latest = text;
        notifyObservers();
    }

    public String getLevel() {
        return level;
    }

    public String getLatest() {
        return latest;
    }
}

// ---------- Concrete Observers ----------
class NoticeScreen implements Observer {
    private final String location;

    public NoticeScreen(String location) {
        this.location = location;
    }

    @Override
    public void update(Subject subject) {
        AlertHub hub = (AlertHub) subject;
        String level = hub.getLevel();
        String text = hub.getLatest();
        System.out.println("[Screen-" + location + "] " + level + ": " + text);
    }
}

class MobileApp implements Observer {
    private final String owner;

    public MobileApp(String owner) {
        this.owner = owner;
    }

    @Override
    public void update(Subject subject) {
        AlertHub hub = (AlertHub) subject;
        String level = hub.getLevel();
        String text = hub.getLatest();
        System.out.println("[App/" + owner + "] push notification - "
                + text + " (" + level + ")");
    }
}

class AlertArchive implements Observer {
    private final List<String> log = new ArrayList<>();

    @Override
    public void update(Subject subject) {
        AlertHub hub = (AlertHub) subject;
        String level = hub.getLevel();
        String text = hub.getLatest();
        log.add(level + ": " + text);
        int count = log.size();
        System.out.println("[Archive] alert #" + count + " stored");
    }
}

The overlap

AlertHub fills two rows of that table. It is the singleton and the concrete subject — the class owns both the lifecycle and the notification. That doubling-up is normal when the one shared object is also the thing that broadcasts, and it is worth naming out loud.

Marking points

  • __new__ overridden, _instance a class attribute, guard is if cls._instance is None — that is what makes it lazy. Boot message prints once, after the opening line.
  • _observers is initialised inside the __new__ guard, not in an __init__. This is the crux of the combined problem: Subject.__init__ doing self._observers = [] would run on every AlertHub() call and wipe the registry, so the security office's alert would reach nobody even though the devices were installed. Note that the reference solution therefore gives Subject no __init__ at all.
  • notify() is called from inside raise_alert, not from the driver.
  • AlertHub never names NoticeScreen, MobileApp or AlertArchive anywhere.
  • FacilitiesDesk and SecurityOffice are unedited in shape — they still call AlertHub() with no arguments. A solution that passes the hub in as a constructor argument has solved the problem by removing it.
  • detach works: the uninstalled app produces no output on the second alert.
  • Identity check prints True.

Java notes — where the translation is not one-to-one

  • The Python trap does not exist in Java. Because a private constructor runs only when an object is really created, the field initialiser private final List<Observer> observers = new ArrayList<>() fires exactly once, and AlertHub needs no constructor guard at all. Python calls __init__ on every AlertHub() — __new__ hands back the same object, then __init__ runs again and would reset self._observers to an empty list, silently unsubscribing everybody. That is why the Python __init__ starts with if hasattr(self, "_level"): return. Worth showing side by side: the same design, one language needing a guard the other does not.
  • In exchange, Java forces the clients to change to AlertHub.getInstance() — the Python brief's “don't edit the clients” rule cannot be honoured.
  • device.getClass().getSimpleName() is the direct equivalent of type(device).__name__.
  • detach during notifyObservers() would throw ConcurrentModificationException without the defensive copy. The driver here detaches between alerts, so it never fires — which is exactly the kind of bug that ships.

Flood Warning Station

The target interface is the observer interface

The story

A river monitoring station takes a water-level reading every few minutes. The moment a new reading arrives, every warning device attached to the station must react immediately — nothing should sit in a loop asking the station whether the level changed. Devices are attached and removed while the station is running (a siren goes for maintenance, a new display is installed), and the station has no idea how many are listening at any moment.

Here is the difficulty. The station's own mobile app was written by your team and can be told whatever you like. The other two devices are field hardware you cannot modify, and neither of them speaks the station's language:

  • The siren does not understand water levels at all. It only accepts a duration in seconds — so somebody has to translate a severity into “how long to wail”.
  • The LED board needs three calls in a fixed order — set line 1, set line 2, commit — and each line must be uppercase and at most 16 characters. Anything longer is simply cut.

The station must not contain a single line of siren-specific or board-specific logic. All it knows is that whatever is attached can be told “a new reading arrived”.

Read it first

Read record_level carefully — it has two separate faults living in one method. It is welded to exactly two devices that were handed to its constructor, and it knows both of their private vocabularies. Each pattern you apply removes one of them.

Your task

  1. Declare the observer interface with a single update(subject) method, and add the subject machinery (attach, detach, notify) to the station. record_level must call notify().
  2. Give the station a severity rule it can be asked for: get_level() returns the reading and get_severity() returns a severity string — DANGER at 6.0 m and above, WARNING at 4.5 m and above, otherwise NORMAL. The severity logic belongs to the station; how a device reacts to it does not.
  3. Adapt the two field devices so they can be attached as observers. Neither has an update method, and neither ever will. Wrap each of them in an object adapter — the adapter holds the device in an adaptee field and calls it. The severity-to-duration mapping and the uppercase/truncate/three-call formatting each live inside their own adapter — not in the station, and not in the driver.
  4. Add one native observer — a MobileApp that implements the observer interface directly, with no adapter. Your station must treat it identically to the two adapted devices.
  5. Driver: attach all three, record a normal reading, record a warning reading, detach the app, record a danger reading.

# ---------- Target / Observer ----------
class Observer(ABC):
    @abstractmethod
    def update(self, subject):
        pass


# ---------- Subject ----------
class Subject:
    def __init__(self):
        self._observers = []

    def attach(self, observer):
        self._observers.append(observer)

    def detach(self, observer):
        if observer in self._observers:
            self._observers.remove(observer)

    def notify(self):
        for observer in self._observers:
            observer.update(self)


# ---------- Concrete Subject ----------
class WaterLevelStation(Subject):
    def __init__(self, river):
        super().__init__()
        self._river = river
        self._level = 0.0

    def record_level(self, meters):
        self._level = meters
        print(f"{self._river}: reading {meters} m")
        self.notify()

    def get_river(self):
        return self._river

    def get_level(self):
        return self._level

    def get_severity(self):                # the rule lives here, once
        if self._level >= 6.0:
            return "DANGER"
        if self._level >= 4.5:
            return "WARNING"
        return "NORMAL"

// ---------- Subject ----------
class Subject {
    private final List<Observer> observers = new ArrayList<>();

    public void attach(Observer observer) {
        observers.add(observer);
    }

    public void detach(Observer observer) {
        observers.remove(observer);
    }

    public void notifyObservers() {
        for (Observer observer : new ArrayList<>(observers)) {
            observer.update(this);
        }
    }
}

The overlap

CardScannerAdapter is doing two jobs at once — it translates the vendor's vocabulary into the target interface, and it guarantees that only one of it exists. It is the natural place for both, because it is the only class in the system that ever touches the device: if the wrapper is unique, the session is unique.

Marking points

  • The vendor SDK is not edited. Any change there is an automatic deduction — the scarcity check inside open_port is what makes the problem real.
  • open_port is called inside the __new__ guard, not in __init__ and not from a client. If the adaptee is constructed in __init__, the second CardScannerAdapter() call builds a fresh SDK and raises the device error — which is exactly the crash the story opens with, now moved somewhere less obvious. This is the trap.
  • _instance is a class attribute and the guard is if cls._instance is None, so the port opens on first scan, not at import.
  • The lookup table exists in exactly one place, inside the adapter. Three copies in three modules means task 2 was not done.
  • No client contains open_port, poll_raw, close_port, or a raw hex string.
  • MaintenanceConsole reports a non-zero scan count without ever scanning. That is the single best evidence the session is shared, and a driver that omits it should lose the task 6 mark.
  • release() closes the port and clears _instance, otherwise the next CardScannerAdapter() hands back a scanner whose port is shut. Students who close without clearing have built an object that lies about its state.

Java notes — where the translation is not one-to-one

  • The Python trap moves. In Java there is no __init__-runs-every-time hazard, so openPort sits safely in the private constructor. The Java version of the same mistake is a non-private constructor: leave it package-private and any module can still write new CardScannerAdapter(), claim a second seat and throw. Making the constructor private is what enforces the invariant.
  • instance = null inside release() assigns a static field from an instance method — legal, and worth flagging in review because it reads as if it only affects that object.
  • Map.of(...) builds an immutable map, so the shared lookup table cannot be mutated by a client that got hold of it. Python's class-level dict has no such protection.
  • The vendor's IllegalStateException is unchecked, so nothing forces a caller to handle it — the crash is a runtime surprise in both languages.

The adapter fixed the vocabulary fault — modules asked for ports and hex tags when they wanted student IDs, and each kept its own translation table. The singleton fixed the scarcity fault — three modules each claiming a device that permits one session. Either alone leaves the other: an adapter without the singleton still lets every module construct its own adapter and crash on the second open_port; a singleton SDK without the adapter stops the crash but leaves all three modules parsing hex and duplicating the lookup table.

A class adapter would inherit from RfidReaderSDK, so CardScannerAdapter is a reader — and every instantiation of it runs the vendor's __init__ and inherits open_port/close_port as part of its own public surface. That undermines both halves at once: the adapter can no longer hide the port lifecycle it was supposed to encapsulate, and clients can call close_port() directly on the shared singleton, shutting the session out from under every other module. Composition keeps the adaptee private, which is what a shared resource needs.

The story

Several night jobs send SMS to students: the result publisher, the library overdue reminder, and an ops dashboard that only reports on what the others did. None of them knows the others exist.

They all go through one telecom gateway, and the licence permits one live session for the whole campus. The SDK does not refuse a second login — it does something worse. Authenticating again silently revokes the previous session, so the job that logged in first keeps running happily and every message it sends after that is quietly rejected. Nothing crashes. Students simply never receive their results.

The session must also not be claimed when the software boots — only the first time some job actually sends a message.

The SDK is vendor code you cannot edit, and it disagrees with your jobs on almost everything:

  • It only accepts batches, a list of dictionaries. Your jobs mostly want to send one message.
  • It wants numbers in international form — 8801712345678 — while campus records store the local form, 01712345678.
  • It reports outcomes as integer codes (0 delivered, 1 bad number, 3 revoked session), while your jobs want a plain true/false.
  • It hands back a session token that has to be carried into every later call.

Right now each job logs in for itself, converts its own numbers, wraps its own batch and reads the raw codes — which is both four copies of the same translation and the reason the sessions keep revoking each other.

    private final String token;

    private int failed = 0;

        this.adaptee = new TeletalkBulkSMS();
        this.token = adaptee.authenticate("campus-key");

        return instance;
    }

        String clean = localNumber.replace(" ", "");
        if (clean.startsWith("+")) {
            clean = clean.substring(1);
        }
        return "88" + clean;
    }

    public boolean send(String number, String text) {
        return sendBulk(List.of(new Message(number, text))).get(0);   // single -> batch of one
    }

        List<Map<String, String>> entries = new ArrayList<>();

            } else {
                failed++;
            }
        }
        return results;
    }

    public String status() {
        return "session live, " + sent + " sent / " + failed + " failed";
    }

        instance = null;

The overlap

CampusSmsAdapter both translates the vendor's vocabulary into the target interface and guarantees only one of itself exists. It is the right place for both because it is the only class that ever holds a token — if the wrapper is unique, the session is unique.

Marking points

  • The vendor SDK is not edited. The revocation behaviour inside authenticate is what makes the problem real.
  • authenticate is called inside the __new__ guard. If the token, the SDK object or the counters are set up in __init__, that __init__ re-runs on every CampusSmsAdapter() call. Two things then go wrong, and neither raises: a fresh session is issued per call (seven session issued lines in the reference driver instead of one), and the counters reset, so OpsDashboard reports 0 sent / 0 failed. The messages still arrive — the shared instance means the new token overwrites the old one — and the identity check still prints True, so the output looks almost right. This is the trap, and the two driver tests in task 7 exist precisely to catch it.
  • _instance is a class attribute, guard is if cls._instance is None, so the session is claimed on first send rather than at import.
  • All four translations live in the adapter: "88" + number, single-to-batch, code == 0, and token carrying. Any of them appearing in a client means task 2 was not done.
  • No client contains authenticate, push_batch, msisdn, a raw dictionary, or an integer code comparison.
  • send delegates to send_bulk. Two independent implementations is a duplication smell — see follow-up 2.
  • Counters are updated in send_bulk only, so they stay correct however messages arrive.
  • OpsDashboard reports a non-zero count without sending anything. That is the best evidence the session is shared; a driver omitting it should lose the task 7 mark.
  • release() closes the session and clears _instance, otherwise the next CampusSmsAdapter() returns an object holding a dead token.

Java notes — where the translation is not one-to-one

  • Python's (number, text) tuple becomes a small Message class — or record Message(String number, String text) {} on Java 16+. Watch how much clearer List<Message> reads than the Python signature's implied “list of pairs”.
  • notify(String, String) would compile — it overloads Object.notify() rather than overriding it — but naming a method notify next to the observer problems in this set is asking for confusion, so the Java version uses notifyStudent.
  • token.equals(liveToken) inside the vendor SDK is null-safe in that direction; liveToken.equals(token) would throw once the session is closed. Objects.equals(a, b) sidesteps the question — a good habit to point at while it is visible.
  • The delivered flags print as true/false in Java and True/False in Python — the Output panel has tabs for both.
  • results.stream().filter(ok -> ok).count() returns a long, which is why the client prints long and int side by side. Python's results.count(True) hides the same distinction.

Follow-up answers

1.Which fault in the given code did the adapter fix, and which did the singleton fix? Could you have applied either one alone? What would still be wrong?

The adapter fixed the vocabulary fault — batches, number formats, status codes and token plumbing repeated in every job. The singleton fixed the scarcity fault — one licensed session that jobs were revoking from one another. Either alone leaves the other: an adapter without the singleton lets each job build its own adapter, each authenticating and killing the last; a singleton SDK without the adapter stops the revocation but leaves every job converting numbers and reading integer codes by hand.

2.send is written in terms of send_bulk. What would be lost if you implemented each separately, and what does that tell you about which of the two is the real adaptation?

If implemented separately, the number conversion, the code-to-boolean mapping and the counter updates all exist twice and will drift the first time one is changed — the same DRY violation the lecture flags in the factory example, appearing here inside an adapter. It also hides which direction the adaptation runs: the vendor SDK is batch-only, so send_bulk is the real adaptation and send is a convenience built on top of it.

The Currency Desk

Cost is the visible reason, consistency is the real one

The story

The finance office runs a nightly billing job for foreign-currency students. Three modules take part: tuition invoicing, scholarship disbursement, and a finance dashboard that issues no money and only reports on the run.

They all need exchange rates from a commercial provider, and every call to that provider is paid — the campus licence allows a handful per day, after which the call throws. So the rate table must be fetched once for the whole run and then reused, and it must not be fetched when the software boots — only the first time some module actually needs a rate.

There is a second reason, and it matters more than the money. Rates move during the night. If each module fetches its own table, two invoices issued minutes apart can be priced at different rates, and the books will not balance. Every figure in a single billing run must come from one table fetched at one moment.

The SDK is vendor code you cannot edit, and it does not speak the language the finance modules want:

  • It hands back the whole table as one CSV-ish string — USD:1.0,BDT:121.35,EUR:0.92,... — where the modules want a number for one specific pair.
  • Every rate in it is relative to USD. The modules mostly need BDT to something else, so the cross rate has to be worked out.
  • It needs a licence handshake first, and the resulting handle carried into every later call.

Right now each module connects for itself, fetches its own table, splits the string itself and works out its own cross rate — which is three copies of the same parsing code, three paid calls, and three snapshots of a moving market.

  4. Make the desk campus-wide. Every CurrencyDeskAdapter() call must return the same object, created lazily, with the fetch happening inside the same guard that creates the instance — so the cache and the object cannot come apart.
  5. Track how many lookups the desk has served, across all modules, and report it through status() along with the number of paid calls used.
  6. Add a refresh() that deliberately spends one more paid call to replace the cached table, for the rare case where finance wants a mid-run re-price.
  7. Rewrite the three modules to use the target interface. The dashboard must be able to report without spending anything.
  8. Driver. Issue at least two invoices and one scholarship payment, through different modules. The “rate table fetched” line must appear exactly once, and the paid-call counter must still read 1 at the end. Two conversions of the same amount, made through two different modules, must produce identical figures. The dashboard must report a lookup count covering the other modules' work. Where this one goes wrong

__init__ runs on every call. If the fetch or the parsed table is set up there, every module re-fetches, the quota drains, and — before it drains — different modules quietly price their figures from different tables.

How this one is judged

There is no fixed expected output. The tests are: more than one paid call means the cache is not shared, and two equal amounts converting to different figures means the run is not consistent.

// ---------- Adapter + Singleton ----------
class CurrencyDeskAdapter implements RateProvider {
    private static CurrencyDeskAdapter instance;

    private final FxRateService adaptee;
    private final String handle;
    private Map<String, Double> table;
    private int lookups = 0;

    private CurrencyDeskAdapter() {                             // fetch and instance cannot come apart
        System.out.println("Opening the currency desk for today...");
        this.adaptee = new FxRateService();
        this.handle = adaptee.connect("campus-licence");
        this.table = load();
    }

    public static CurrencyDeskAdapter getInstance() {           // lazy creation
        if (instance == null) {
            instance = new CurrencyDeskAdapter();
        }
        return instance;
    }

    private Map<String, Double> load() {
        String raw = adaptee.fetchRates(handle, "USD");            // one paid call
        Map<String, Double> parsed = new LinkedHashMap<>();
        for (String pair : raw.split(",")) {                       // CSV string -> doubles
            String[] kv = pair.split(":");
            parsed.put(kv[0], Double.parseDouble(kv[1]));
        }
        return parsed;
    }

    @Override
    public double rate(String fromCcy, String toCcy) {
        lookups++;
        return table.get(toCcy) / table.get(fromCcy);              // cross rate via USD
    }

    @Override
    public double convert(double amount, String fromCcy, String toCcy) {
        return Math.round(amount * rate(fromCcy, toCcy) * 100.0) / 100.0;
    }

    @Override
    public String status() {
        int cached = table.size();
        int used = adaptee.callsUsed();
        return cached + " currencies cached, " + lookups + " lookup(s) served, "
                + used + "/" + FxRateService.QUOTA + " paid calls used";
    }

    public void refresh() {
        this.table = load();                                       // deliberate second call
    }
}

The overlap

CurrencyDeskAdapter translates the vendor's vocabulary into the target interface and guarantees only one of itself exists. One wrapper means one table, which means one paid call and one consistent set of figures.

Marking points

  • The vendor SDK is not edited. The quota check inside fetch_rates is what makes the problem real.
  • connect and fetch_rates are called inside the __new__ guard. If the fetch happens in __init__, every CurrencyDeskAdapter() call re-fetches: the quota drains after three modules, and — more seriously — figures produced before the drain come from different tables. This is the trap.
  • _instance is a class attribute, guard is if cls._instance is None, so nothing is fetched at import.
  • Parsing, the cross-rate division, the handle, and the rounding all live in the adapter. Any of them appearing in a finance module means task 2 was not done.
  • No client contains connect, fetch_rates, split(","), or a division by table["BDT"].
  • convert delegates to rate. Two independent implementations of the arithmetic is a duplication smell.
  • refresh() re-fetches and replaces the table, without creating a second instance. A refresh that clears _instance would let the old desk's users keep a stale table — check for that.
  • The dashboard reports a non-zero lookup count while spending nothing. Best single piece of evidence the desk is shared; a driver omitting it should lose the task 8 mark.
  • Two conversions of 90000 BDT through two different modules must print the same figure to the last decimal.

Java notes — where the translation is not one-to-one

  • Python's round(x, 2) and Java's Math.round(x * 100.0) / 100.0 agree here, but they are not the same function: Python 3 uses banker's rounding (round(2.5) is 2), Java rounds half up. On money, neither is really right — BigDecimal with an explicit RoundingMode is.
  • LinkedHashMap rather than HashMap so status() and any future dump list currencies in the order the vendor sent them. Python dicts have kept insertion order since 3.7, which is why the Python version needs no equivalent choice.
  • table is not final — refresh() replaces it. Everything else in the desk is final, which is a useful signal in review: the one mutable field is the one thing that is meant to change.
  • The vendor's calls counter is static, so it survives refresh() and any new instance — which is exactly why the quota is a global budget and no amount of object juggling on your side escapes it.

Follow-up answers

1.Which fault in the given code did the adapter fix, and which did the singleton fix? Could you have applied either one alone? What would still be wrong?

The adapter fixed the vocabulary fault — a CSV string, a USD-relative table and a licence handle, re-parsed in every module. The singleton fixed the shared resource fault — one paid quota and one cached snapshot. Either alone leaves the other: an adapter without the singleton has every module building its own desk, fetching its own table and blowing the quota; a shared SDK object without the adapter stops the extra calls but leaves three copies of the parsing and cross-rate code, which is where a rounding or direction bug will eventually differ between modules.

2.This problem gives two reasons for having one desk: cost and consistency. Which one would still justify the singleton if the provider were free and unlimited? Which is the stronger argument, and why?

Consistency survives a free, unlimited provider — rates move whether or not calls are billed, so a run that fetches twice can still price two invoices differently. That makes it the stronger argument: cost is a budget problem that a bigger licence solves, while inconsistency is a correctness problem that no licence fixes. A good answer notices that the money is the visible reason and the consistency is the real one.

The story

The university IT helpdesk runs three desks: hardware, software and network. Each desk raises a different kind of ticket — they carry different response deadlines and print differently — but every desk follows the exact same routine when a complaint arrives: take a tracking number, create the ticket, file it, and tell the reporter the deadline. That routine never changes. What changes is which kind of ticket a given desk produces. A desk knows when a ticket must be created, not what kind.

Cutting across all three desks is the ticket log. There must be exactly one log for the whole helpdesk, because it does two jobs that only work if nothing is duplicated:

  • It issues the tracking numbers, in one unbroken sequence. TKT-0001, TKT-0002, TKT-0003 — and a number must never be handed out twice, no matter which desk asked for it.
  • It holds every ticket raised today, so the supervisor's console — which raises no tickets of its own and belongs to no desk — can list all of them at the end of the shift.

The log must also not open when the helpdesk software boots; it should be created the first time some desk actually needs a number.

Read it first

Your task

  1. Guarantee one registry. Every TicketRegistry() call must hand back the same object, created lazily. TicketDesk and SupervisorConsole must keep calling TicketRegistry() exactly as they do now — you may not edit them to receive the registry as an argument.
  2. Give the three ticket classes a common product interface with sla_hours() and describe(). Lift the shared __init__ into it.
  3. Turn TicketDesk into the creator. open_ticket keeps the shared routine, but the ticket it files comes from an abstract factory method. open_ticket must no longer take a kind argument, and no concrete ticket class name may appear inside it.
  4. Write one concrete creator per desk — HardwareDesk, SoftwareDesk, NetworkDesk. The if/elif chain must disappear completely.
  5. Driver. Open at least four tickets through at least three different desks, interleaved — not all the hardware ones first. The printed tracking numbers must form one unbroken sequence with no repeat, which is only possible if the registry is shared. Then call the supervisor's console, which belongs to no desk, and show it can see every ticket raised. Print an identity check on the registry.

Where this one goes wrong

How this one is judged

The overlap

Unlike the earlier combined problems, no class here plays two roles. The two patterns meet in one line of open_ticket — the creator's invariant routine asks the singleton for a tracking number, then passes it into the factory method. The singleton is what makes the number unique across creators; the factory method is what lets one routine serve three desks. That is collaboration, not the interface overlap the adapter combinations had.

Marking points

  • __new__ overridden on TicketRegistry, _instance a class attribute, guard is if cls._instance is None. The log message prints once, after the opening line, and only when the first ticket is raised.
  • _counter and _tickets are initialised inside the __new__ guard (or behind an _initialised flag). A plain __init__ assigning self._counter = 0 runs on every TicketRegistry() call, so every desk resets the sequence — the tickets all come out as TKT-0001, and the supervisor sees no tickets at all: the console's own TicketRegistry() call wipes the list one last time before summary() reads it. This is the trap — and note the identity check still prints True, so the registry looks shared even while it is being emptied.
  • open_ticket takes only (reporter) — no kind. If kind survives, the factory method was not applied.
  • No concrete ticket class name appears inside open_ticket, and no if/elif on a type string appears anywhere in the file.
  • create_ticket is abstract on TicketDesk and overridden in each concrete desk.
  • SupervisorConsole is unedited and still calls TicketRegistry() with no arguments. A solution that passes the registry in as a constructor argument has removed the problem instead of solving it.
  • Driver interleaves desks and the numbers still run 0001, 0002, 0003, 0004. A driver that opens all tickets through one desk proves nothing and should lose the mark for task 5.

Java notes — where the translation is not one-to-one

  • String.format("TKT-%04d", counter) is the direct equivalent of Python's f"TKT-{c:04d}".
  • Ticket is an abstract class, not an interface, because the two fields and the shared constructor live in it — task 2's “lift the shared __init__ into it” only has a home in a class. Contrast with Shipment and Report in the Set A/B factory problems, which are pure behaviour and therefore interfaces. That is the practical rule for choosing between the two.
  • Look at the given Java's summary(): with no supertype, the log needs an instanceof chain just to print, and every new ticket kind reopens it. That is a second closed-for-modification violation the Python version hides behind duck typing.

Part B (optional, for those who finish early) — answer

Written as if cls._instance is None, each desk does get its own instance. The reason is one rule of the Python data model: attribute lookup walks the MRO up to the base, but attribute assignment binds on the object you assign to — and inside __new__, cls is the concrete subclass. So HardwareDesk() finds the inherited None, then writes _instance onto HardwareDesk itself; SoftwareDesk still sees the base's None and creates its own. Each subclass ends up with a private _instance, and TicketDesk._instance stays None forever.

Written as if TicketDesk._instance is None, the guard both reads and writes the base attribute, so the first desk instantiated wins and every later desk returns that object — SoftwareDesk() hands back a HardwareDesk:

>>> type(HardwareDesk()).__name__, type(SoftwareDesk()).__name__
('HardwareDesk', 'HardwareDesk')

A student who writes the second form and does not test it will produce a program that runs happily and files every ticket to the wrong desk. Worth noting that the first form's correctness is accidental rather than declared — an explicit _instances = {} dict keyed by cls says what is meant and cannot be misread.

On the design question itself: making stateless desks singletons buys nothing. Object creation is cheap, and the constraint being encoded (“there is only one hardware desk”) is not a real invariant of the domain the way “there is only one ticket log” is. This is the sanity check worth teaching — Singleton earns its place only when duplication causes a visible fault. Here duplication of a desk causes none.

In Java

In Java this experiment cannot even be run. A private static TicketDesk instance on the base class is one field shared by every subclass — Java has no per-subclass attribute shadowing, so there is no cls to bind to. The Java version always behaves like the TicketDesk._instance form: SoftwareDesk.getInstance() returns the HardwareDesk. The fix is the same one that is also the better Python answer — an explicit Map<Class<?>, TicketDesk> keyed by the concrete class. Python's accidental correctness and Java's honest breakage point at the same design.
